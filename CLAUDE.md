# kiawosch-cms

pnpm monorepo (`pnpm@11`). Two Next.js apps under `apps/` — `@kiawosch/backend`
(Payload CMS, port 5000) and `@kiawosch/website` (port 5001) — plus shared
config in `packages/`.

## Next.js 16: use `proxy.ts`, not `middleware.ts`

Both apps run Next.js 16, which renamed the `middleware.ts` file convention to
`proxy.ts` (same file, the exported function is renamed from `middleware` to
`proxy`). Never create or restore a `middleware.ts` file — Next.js logs a
deprecation warning on every dev-server start if one exists. `apps/website/proxy.ts`
is the locale-redirect proxy; edit it in place rather than reintroducing
`middleware.ts`.

## Never gate on runtime env vars inside `proxy.ts`

Next.js **inlines module-scope `process.env` reads into the proxy/middleware
bundle at build time**. A var that is absent during `next build` (the Docker
image builds without a `.env`, since it is git-ignored) is frozen as
`undefined` forever — setting it on the host at runtime has no effect.

Put such gates in a **server component** instead, which reads `process.env` at
request time. The under-construction gate works this way: `proxy.ts` only sets
an `x-pathname` header, and `app/layout.tsx` calls the helpers in
`app/lib/under-construction.ts` to decide whether to `redirect()`. That makes
`UNDER_CONSTRUCTION`, `UNDER_CONSTRUCTION_PERCENT`, and `INFO_REDIRECT_URL`
togglable with a container restart, no rebuild.

Note the standalone runner (`node apps/website/server.js`) does **not** load
`next.config.ts`, so the root-`.env` loader there only applies to dev/build.
Production values must be real environment variables (see the `website`
service in `docker-compose.yml`).

## Codemap — understanding the dependency graph

Before working on unfamiliar code, or when you need to trace how modules connect
in an app, generate and read the codemap. It is produced by
[dependency-cruiser](https://github.com/sverweij/dependency-cruiser) and is the
fastest way to see the import graph without opening every file.

```bash
pnpm codemap            # regenerate all graphs (backend + website)
pnpm codemap:backend    # backend only
pnpm codemap:website    # website only
```

Outputs land in each app's own `.codemap/` folder (git-ignored, regenerate as needed):

- `apps/backend/.codemap/backend.txt` / `apps/website/.codemap/website.txt` — flat
  `A → B` import list. **Grep this** to find who imports a module or what a file
  depends on.
- `apps/backend/.codemap/backend.mmd` / `apps/website/.codemap/website.mmd` —
  Mermaid `flowchart` grouped by folder. Render or read for the high-level
  structure.

Config lives in `.dependency-cruiser.cjs` (shared) plus a `tsconfig.codemap.json`
in each app. node_modules, build output (`.next`/`dist`), generated files
(`payload-types.ts`, `importMap.js`, `next-env.d.ts`), and tests are excluded so
the graph shows only hand-written source. Each app is cruised from its own
directory with its own tsconfig because the two apps use conflicting `@/*`
path-alias roots.

When the graph looks stale after refactoring, rerun `pnpm codemap` before
reasoning about it.

# Code maps (read these before broad code searches)

Each app has its own dependency map in `apps/<app>/.codemap/`, generated by
dependency-cruiser (node_modules and tests excluded):

- `apps/<app>/.codemap/<app>.txt` — flat `from → to` dependency listing.
  **Grep-friendly; consult this first** when tracing which modules import what.
- `apps/<app>/.codemap/<app>.mmd` — Mermaid graph of the same, for rendering.

When you need to understand an app's structure or find a module's dependents,
read that app's `.codemap/<app>.txt` before falling back to a repo-wide search.

Regenerate after structural changes (added/moved/renamed modules):

```
pnpm codemap
```

Config: `.dependency-cruiser.cjs`. Generator: `scripts/generate-codemaps.mjs`.

# Docker & docker-compose rules

These apply to every Dockerfile and compose file in this repo. They exist
because of hard-won deploy failures on the Iran-hosted Dokploy server —
follow them exactly.

## Registries (the host cannot reach docker.io or registry.npmjs.org)
- Base images: pull from the Arvan mirror, e.g.
  `FROM docker.arvancloud.ir/library/node:22`. Never bare `FROM node:22`.
- npm/pnpm packages: use the Liara mirror
  `https://package-mirror.liara.ir/repository/npm/`.
  Pass it via an `ARG NPM_REGISTRY=…` and `--registry=$NPM_REGISTRY` /
  `pnpm config set registry $NPM_REGISTRY`.

## Package manager
- Use **pnpm**, installed with **`npm install -g pnpm@<pinned>`**.
  NEVER use corepack (its keyid/signature verification is broken on the host).
  Pin the pnpm version to match the lockfileVersion.
- NEVER use `npm ci` — it hard-fails when the lockfile drifts from
  package.json. Use `pnpm install` (or `npm install`).
- NEVER use `--frozen-lockfile`. If you want lockfile preference without a
  hard fail, use `--prefer-frozen-lockfile`.
- Production installs: `pnpm install --prod`.
## Build cache (make deploys fast + resilient)
- Cache the package manager store across builds with BuildKit cache mounts:
  `RUN --mount=type=cache,target=/pnpm-store pnpm install … --store-dir=/pnpm-store`
  and `--mount=type=cache,target=/root/.npm` for the npm step.
- `type=cache` mounts survive `--no-cache` rebuilds; don't rely on layer cache
  for them.
- Keep the host's Dokploy "Docker Cleanup" OFF and set a BuildKit
  `builder.gc.defaultKeepStorage` ceiling so the cache isn't auto-evicted.
## Image conventions
- `EXPOSE ${PORT}` and read the same `PORT` env in the app.

# Env files

Never edit `.env` or `.env.example` unless explicitly asked. They must stay in sync — same keys, comments, and order — and differ only in their values.
